# Example: How the Project Works After Transformation

## Scenario: User creates a capability and authorizes a spend

### BEFORE (Docker-Backed Architecture)

```
User clicks "Commit private capability" in UI
     ↓
web/App.tsx → commitCapability() → useMoatClient() → MockMoatClient
     ↓
creates deterministic SHA-256 fixtures in browser memory only
     ↓
User fills policy form → PolicyBuilder.submit() → api/createCapability
     ↓
api/MockMoatClient.createCapability() → asserts policy, generates random secrets
     ↓
returns capabilityId, policyCommitment, spendStateCommitment (all demo fixtures)
     ↓
UI shows: "Capability created" with mock data
     ↓
No Docker needed - everything runs in browser

--- AUTHORIZE SPEND ---

User clicks "Run CodeShield" → runAuthorization() → client.authorizeSpend()
     ↓
MockMoatClient.authorizeSpend() → runs 7 proof steps deterministically
     ↓
Returns approved/rejected status with demo receipt, nullifier, destination
     ↓
UI updates: shows proof steps, receipt, budget/uses decremented
     ↓
Docker not involved - purely client-side deterministic simulation
```

**Problem**: No real blockchain interaction, no Midnight network, just browser fixtures.

---

### AFTER (Database-Backed Architecture with Template)

```
User clicks "Commit private capability" in UI
     ↓
web/App.tsx → commitCapability() → useMoatClient() → [SELECTABLE]
     ├─ Demo mode: MockMoatClient (no backend needed)
     ├─ Midnight: RealMoatClient + database provider
     └─ zk: ZkMoatClient + database provider
     ↓
API layer → database.createCapability(input) → persists to DB
     ↓
Database stores: capabilityId, policyCommitment, spendStateCommitment,
                 alias, agentName, perTransactionLimit, totalBudget, maxUses, allowedCategory
     ↓
API returns: capabilityId + commitments (same shape as before)
     ↓
UI shows: "Capability created" with same UI display
     ↓
Database persists state for later operations

--- AUTHORIZE SPEND ---

User clicks "Run CodeShield" → runAuthorization() → client.authorizeSpend()
     ↓
RealMoatClient.authorizeSpend() → BUT first checks database for capability state
     ↓
Database query: SELECT * FROM capabilities WHERE capabilityId = ?
     ↓
If found: validates policy constraints against DB stored state
     ↓
If valid: updates DB: decrement usesRemaining, decrement remainingBudget
     ↓
Generates receipt Commitment, nullifier, stores in DB
     ↓
API returns: approved status with receipt (same shape as mock)
     ↓
UI updates: same display, but state now in database

--- SWITCH BACKENDS ---

To change from Midnight to zk backend:
1. Change config: MIDNIGHT_NETWORK → ZK_NETWORK (or similar)
2. API uses ZkDatabaseProvider instead of MidnightDatabaseProvider
3. UI shows IDENTICAL interface - same fields, same flow
4. Only the database adapter implementation changes
```

## Concrete Flow: Create + Authorize with SQLite Backend

```
1. User enters: alias="Research", agent="Agent A", 
   perTx="10", totalBudget="100", maxUses="3", category="developer-tools"

2. UI → API → SQLiteProvider.createCapability(input)
   ↓
   DB INSERT: capabilities table
   └─ capabilityId: "cap_demo_abc123"
   ├─ policyCommitment: "0x1234...abcd"
   ├─ spendStateCommitment: "0x5678...efgh"
   └─ status: "active", usesRemaining: 3, remainingBudget: "100"

3. API returns to UI → UI displays: "Capability created"

4. User → "Run CodeShield" → client.authorizeSpend({capabilityId, request})
   ↓
   API → SQLiteProvider.authorizeSpend(...)
   ↓
   DB SELECT: GET capabilities WHERE id = "cap_demo_abc123"
   ↓
   Validate: amount ≤ perTx limit, budget has enough, category matches
   ↓
   DB UPDATE: usesRemaining → 2, remainingBudget → 90
   ↓
   Generate: receiptCommitment, nullifier (SHA-256 fixtures)
   ↓
   DB INSERT: receipts table (capabilityId, requestCommitment, receiptCommitment, nullifier)
   ↓
   API returns: { status: "approved", receipt: {...} }
   ↓
   UI shows: receipt, nullifier, budget updated to 90, uses remaining 2
```

**Note**: Same UI display as before. Same API return shape. Only the backend (SQLite vs Midnight vs zk) is different.

## What Changes vs What Stays the Same

| Stays the Same | Changes |
|----------------|---------|
| `MoatClient` interface (`web/src/services/moat-client.ts`) | `api/src/providers.ts` → database-agnostic |
| `web/App.tsx` UI components | Database schema design |
| `web/src/types/domain.ts` types | API route handlers |
| `contract/src/moat.compact` (if using Midnight) | `local:*` npm scripts (replace with DB ops) |
| Authorization flow logic | `.env.example` (replace Docker vars with DB vars) |
| Receipt verification logic | Docker compose (optional, keep for legacy) |
| Proof step pipeline | New `DatabaseProvider` interface + implementations |
| Capability policy validation | Backend-specific adapters (Midnight/zk/etc.) |

## Starting Implementation Example

**Step 1**: Add SQLite dependency and create database layer

```bash
# Add SQLite
npm install better-sqlite3

# Create api/database directory
mkdir api/database

# Create abstract interface
cd api/database
touch index.ts         # exports DatabaseProvider interface
touch sqlite.ts        # implements DatabaseProvider using better-sqlite3
```

**Step 2**: Update API to use database instead of Midnight providers

```typescript
// api/src/providers.ts - simplified
export function createMoatProviders(input: CreateMoatProvidersInput): MoatProviders {
  const { backend = 'sqlite', databaseUrl } = input;
  
  switch (backend) {
    case 'sqlite':
      return new SqliteProvider(databaseUrl).toMootProviders();
    case 'midnight':
      return new MidnightProvider(databaseUrl).toMootProviders();
    case 'zk':
      return new ZkProvider(databaseUrl).toMootProviders();
    default:
      throw new Error(`Unknown backend: ${backend}`);
  }
}
```

**Step 3**: UI continues working exactly as before - no changes needed because it depends on the abstract `MoatClient` interface.

**Step 4**: Run tests - existing `vitest` tests should pass with SQLite backend since MockMoatClient logic is replicated in the database operations.

## Result

- **No Docker needed** for basic functionality (SQLite or in-memory DB suffices)
- **Same UI/UX** - users see identical interface
- **Swap backends** by changing config, not code
- **Persisted state** - capabilities survive page refresh (unlike current demo mode)
- **Ready for production** - just swap SQLite → Midnight/zk database adapter
